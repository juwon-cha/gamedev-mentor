# 작성·검수 기준

이 문서는 GameDev Mentor의 문제를 만들고 검수할 때 따르는 기준입니다. 학습자도 "이 문제의 내용을 어디까지 믿어도 되는가"를 판단할 수 있도록 정리했습니다. 문제 스키마의 필드 하나하나는 [README.md](../README.md#문제-스키마)에 있습니다.

**가장 중요한 원칙은 잘못된 내용 0입니다.** 학습자는 문제·해설·채점표를 사실로 믿고 면접을 준비합니다. 틀린 문장 하나가 잘못된 지식으로 굳으므로, 문제 수보다 정확성을 앞에 둡니다. 확인되지 않은 내용은 빼거나, 범위를 좁히거나, "추론"으로 표시합니다.

## 1. 출처

### 1-1. 우선순위

| 순위 | 종류 | 예 | 문장에 쓰는 방식 |
|---|---|---|---|
| 1 | **계약**: 무엇이 보장되는가 | 공식 API·개념 문서(Microsoft Learn, Unity 매뉴얼·스크립팅 API, cppreference), 언어 표준(C# 표준, C++ 표준) | 규칙으로 씁니다 |
| 2 | **구현**: 특정 버전이 실제로 무엇을 하는가 | dotnet/runtime `release/8.0` 소스, microsoft/STL, libstdc++, roslyn (태그나 커밋에 고정한 링크) | ".NET 8 구현에서는 …"처럼 버전을 붙이고, 보장처럼 쓰지 않습니다 |
| 3 | **팀의 설명** | .NET Blog, DirectX Developer Blog, Book of the Runtime(BOTR) | 작성자·날짜와 함께 인용하고, 계약으로 끌어올리지 않습니다 |
| 4 | **대학 강의 슬라이드** | Carnegie Mellon 15-418, 15-362, 17-214 | 개념 설명용입니다. 엔진·런타임·API 사실의 근거로는 1~3순위보다 아래입니다 |

- **강의 영상은 사실 근거로 쓰지 않습니다.** 문장 단위로 대조할 수 없기 때문입니다. "더 공부할 거리"로만 소개합니다.
- 게임 플랫폼 서비스 문서(PlayFab, GDK)는 그 제품의 설계로 소개하고, 보편적인 사실처럼 쓰지 않습니다.
- 동작이 버전에 따라 다르면 버전을 밝힙니다: .NET 8, Unity 6, C++17, g++ 13 등.
- 존재하지 않는 API를 지어내지 않고, 어떤 문서가 하지 않은 말을 그 문서의 말로 돌리지 않습니다.

### 1-2. 출처 표시

- 문제의 `sourceRefs`에 근거 문서 id를 최대 4개 둡니다. id는 공통 레지스트리 `data/sources.json`이나 같은 트랙 파일의 `extraSources`에 선언되어 있어야 합니다.
- 특정 페이지·파일·절을 가리키는 깊은 링크는 트랙 파일의 `extraSources`에 둡니다. 같은 id는 어디서나 같은 주소를 가리켜야 합니다(`tools/validate-data.js`가 검사합니다).
- 해설 본문에는 문장 끝에 `[자료-id]`로 근거를 붙입니다.
- 전체 자료 목록과 각 자료를 인용한 문제는 [SOURCES.md](SOURCES.md)에 있습니다.

### 1-3. 확인 방법

- 사실 주장은 **1차 출처 원문을 그때 받아서** 문장을 찾아 대조합니다(예: `curl`로 원문을 받고 `grep`으로 해당 문장 확인). 기억이나 요약에 기대지 않습니다.
- 코드의 동작과 수치(할당 바이트, 시간, 복잡도)는 **실행해서** 확인합니다. 어느 환경에서 실행했는지(.NET 8, g++ 13 등) 함께 적습니다.
- Unity 엔진 안에서 직접 실행하지 못한 주장은 문서 근거만으로 쓰고, 그 사실을 밝힙니다.

## 2. 문제 형식

### 2-1. 모드별 요구

| 모드 | 화면 이름 | 반드시 들어가는 것 |
|---|---|---|
| `tutoring` | 과외·개념 | 게임 개발 비유가 있는 개념 카드(`concept`)와 셀프 체크 퀴즈 1~2개(`quiz`). 작은 실습 코드가 붙을 수 있습니다 |
| `interview` | 압박 면접 | 시나리오 안의 메인 질문(굵게)과 점점 깊어지는 꼬리질문 정확히 3개(`followUps`: 질문·의도·모범 답변) |
| `debugging` | 디버깅 | 실제 버그 2~3개가 든 초기 코드(주석으로 힌트를 주지 않음), 버그마다 해설에 실패하는 구체적 입력, 3단계 힌트 |
| `implementation` | 실전 구현 | 시그니처만 있는 초기 코드, 제약(시간·공간 복잡도, 금지된 라이브러리 지름길), 엣지 케이스 2~5개, 3단계 힌트 |

- **힌트 3단계:** ① 개념이나 반례 입력 → ② 위치를 좁히되 고치는 방법은 말하지 않음 → ③ 핵심을 비운 의사코드 골격. 3단계도 정답을 그대로 주지 않습니다.
- **해설:** 접근 방법, 왜 맞는지, 복잡도, 흔한 실수를 시니어의 눈으로 설명하고, 마지막은 "흔한 오해" 절로 끝냅니다(4절).
- 모든 문제는 실제 게임 개발 상황(전투, 스킬, AI, UI, 네트워크, 렌더링 등)을 배경으로 합니다.

### 2-2. 난이도

주니어 게임 프로그래머를 기준으로 모든 트랙에 같은 잣대를 씁니다.

| 난이도 | 화면 표시 | 기준 |
|---|---|---|
| `Easy` | 쉬움 | 개념 하나, 짧은 코드나 1차 면접 질문. 준비된 주니어가 10~15분 안에 풉니다 |
| `Medium` | 보통 | 개념 두세 개를 엮거나, 엣지 케이스가 실제 일의 대부분입니다. 20~40분 |
| `Hard` | 어려움 | 성능 제약, 설계 트레이드오프, 서로 얽힌 여러 버그, 또는 일반적인 주니어 면접을 넘는 3단계 꼬리질문 |

**묶음별 분포:** 확장 묶음은 여섯 문제면 쉬움 2 · 보통 2 · 어려움 2, 다섯 문제면 2 · 2 · 1(주제가 무거우면 1 · 2 · 2)로 맞춥니다. 검수자는 실제 난이도를 같은 잣대로 다시 판정하고, 목표에서 벗어나면 이름표를 바꾸기보다 범위(엣지 케이스, 제약, 꼬리질문 깊이)를 조정해 분포를 지킵니다. 이름표만 바꾸는 것은 조정하면 문제가 망가질 때뿐입니다.

## 3. 채점표

### 3-1. 범주와 배점

`rubric.criteria[]`의 배점은 정수이고 합계는 정확히 100점입니다. 범주별 합계는 고정입니다.

| 범주 | 배점 | 무엇을 보는가 |
|---|---|---|
| 정확성 | 35 | 요구한 동작을 모든 엣지 케이스에서 맞게 하는가, 면접 답변의 핵심 사실이 맞는가 |
| 메모리·성능 | 30 | 시간·공간 복잡도 제약, 불필요한 할당·복사, 캐시·GC 영향 |
| 엔진·언어 규약 | 20 | 언어 표준과 엔진(Unity 등)의 규칙과 관례를 지키는가 |
| 아키텍처·가독성 | 15 | 책임 분리, 이름, 확장하기 쉬운 구조, 읽기 쉬운 코드 |

- 항목마다 학습자가 자기 코드나 답변을 보고 **예/아니오로 확인할 수 있게** 씁니다.
- 모범 답안은 100점을 모두 받아야 하고, 문제가 요구하지 않은 것을 요구하는 항목, 해설과 모순되는 항목은 두지 않습니다.

### 3-2. 치명적 감점

`rubric.criticalDeductions[]`는 실무에서 바로 반려될 실수 2~3개이고, 각각 −10 ~ −30점입니다(예: "−20: 라이브러리 정렬을 호출해 구현을 우회했다", "−20: 시간복잡도가 제약을 넘는다").

### 3-3. 등급

| 등급 | 점수 |
|---|---|
| Pass | 85점 이상 |
| Borderline | 60~84점 |
| Retry | 59점 이하 |

### 3-4. 채점 항목의 근거 표시

채점 항목과 치명적 감점에는 그 항목이 왜 맞는 기준인지 근거를 붙입니다.

- **`sourceId`:** 그 항목이 보상하거나 감점하는 내용을 실제로 뒷받침하는 문서의 id. 뒷받침하지 않는 문서를 형식적으로 붙이지 않습니다.
- **`basis`:** 문서 대신 근거의 종류를 밝힙니다. 값은 둘 중 하나입니다.
  - `"principle"` (화면 표시 "일반 원칙"): 항목 설명 자체에 밝힌 일반 공학 원칙(가독성, 이름 짓기, 관심사 분리 등)을 채점합니다.
  - `"tests"` (화면 표시 "테스트로 확인"): 숨은 테스트가 바로 그 동작을 확인합니다.

최종 점검을 마친 트랙은 모든 항목이 `sourceId`와 `basis` 중 적어도 하나를 가지며, `node tools/validate-data.js --strict-basis`로 검사합니다. 현황은 [VERIFICATION.md](VERIFICATION.md)의 요약에 있습니다.

## 4. "흔한 오해"

모든 해설은 `### 흔한 오해` 절로 끝납니다. AI 도우미나 포럼 답변이 자신 있게 말하는, 그럴듯하지만 틀린 주장을 알아보는 연습입니다.

```
### 흔한 오해
- **"사람들이 실제로 말하는 방식의 틀린 주장"** — 왜 틀렸는지(또는 어떤 조건에서만 맞는지) 한두 문장, 바른 설명과 근거 [자료-id]
```

- 문제마다 1~2개, 그 문제의 주제와 바로 이어진 것만 씁니다.
- 실제로 퍼져 있고 그럴듯한 주장이어야 합니다. 아무도 믿지 않는 허수아비 주장은 쓰지 않습니다. 이전 검수에서 실제로 잡힌 오류가 좋은 재료입니다(예: "noexcept가 없으면 vector는 재할당 때 항상 복사한다", "Single.Epsilon은 기계 엡실론이다").
- 바로잡는 문장은 다른 주장과 똑같이 검증합니다. 연 문서의 id를 붙이거나, 실행 결과("판정 서버(.NET 8)에서 실행해 확인")를 밝힙니다. 조건에 따라서만 틀린 주장이면 그 조건을 적습니다.
- 같은 트랙 안에서 같은 오해를 반복하지 않습니다.

## 5. 실행 채점

순수 C#/C++ 코드로 풀 수 있는 디버깅·구현 문제에는 숨은 테스트(`tests`)를 붙입니다. 형식은 [README.md](../README.md#실행-채점용-테스트-tests)에 있습니다.

### 5-1. 테스트 규칙

- **모범 답안은 모든 케이스를 통과하고, 초기 코드는 하나 이상 실패**해야 합니다. `node tools/check-tests.js <파일> [문제id]`가 이를 확인합니다.
- 테스트는 결정적이어야 합니다(고정 시드). 케이스 하나가 실패하거나 예외를 던져도 나머지는 계속 실행됩니다. 케이스는 5~8개, 전체 3초 안팎입니다.
- 검수자는 **틀린 답안 변형**(엣지 케이스나 채점표에 나온 흔한 실수)을 직접 만들어 테스트가 잡는지 확인하고, **다르게 쓴 정답 풀이**가 부당하게 떨어지지 않는지도 확인합니다(지나치게 엄격한 출력 형식, 정확한 할당 횟수, `note`에 밝히지 않은 시그니처 요구 등).
- 타이밍·동시성 테스트는 판정 서버의 캐시를 피해(소스에 주석을 덧붙임) **여러 번 실행**해서, 초기 코드가 매번 실패하고 모범 답안이 매번 통과하는지 확인합니다.
- 정의되지 않은 동작(UB)의 특정 결과에 기대는 테스트는 만들지 않습니다. 불가피하게 판정 서버에서 관찰된 동작에 기대는 경우에는 그것이 표준의 보장이 아니라는 점을 문제와 해설에 밝힙니다.
- 테스트로 안정적으로 잡을 수 없는 버그(예: 일부 데이터 경쟁)는 채점표로만 확인하고, 문제 설명이 그 한계를 숨기지 않게 합니다.
- 테스트는 절대 멈춰 있으면 안 됩니다. 무한 루프가 될 수 있는 케이스는 시간 제한을 둡니다.

### 5-2. 판정 서버의 조건과 한계

판정 서버는 무료 공개 서비스인 Compiler Explorer(godbolt.org)입니다.

| 항목 | 내용 |
|---|---|
| 컴파일러 | C#: .NET 8(`dotnet80csharpcoreclr`) · C++: GCC 13.2(`g132`), `-std=c++17 -O1` |
| 출력 형식 | 케이스마다 표준 출력에 `[PASS] id` 또는 `[FAIL] id :: 사유` 한 줄 |
| 코어 | 2개. 스레드가 약 12개를 넘으면 메모리 부족이 납니다 |
| 시간 | 20초가 지나면 강제 종료됩니다 |
| 캐시 | 같은 소스는 캐시된 결과를 돌려줍니다 |
| 빈도 제한 | HTTP 429가 나므로 짧은 간격으로 많이 보내지 않습니다 |

- 메모리 할당 판정은 .NET 8 기준이고 Unity 런타임(Mono, IL2CPP)과 다를 수 있습니다.
- 시간 기준이 있는 테스트는 판정 서버의 속도에 따라 여유가 달라질 수 있습니다. 정답과 오답의 차이가 충분히 큰 기준만 씁니다.
- libstdc++ 디버그 모드를 쓰는 C++ 템플릿은 진단 메시지가 출력 형식을 깨지 않도록 `GLIBCXX_DEBUG_MESSAGE_LENGTH`를 설정합니다.
- Unity API에 기대는 문제는 실행 채점 대상이 아닙니다. 예외적으로 Unity 동작을 순수 C#으로 흉내 낸 모델 위에서 채점하는 문제는, 어떤 동작이 문서를 따르고 어떤 동작이 모델의 선택인지 시나리오에 밝힙니다.

## 6. 검수 절차

1. **작성:** 작성 에이전트가 이 기준과 묶음별 주제 목록에 따라 문제를 씁니다. 작성자는 `verified`를 붙이지 않고, 확신이 없는 부분을 보고에 남깁니다.
2. **독립 검수:** 작성에 참여하지 않은 검수 에이전트가 문제마다 사실, 출처, 코드, 숨은 테스트, 채점표, 교육적 일관성, 난이도를 확인하고 틀린 곳을 바로 고칩니다. 작성자의 확신은 증거로 보지 않습니다. 자기 작업을 자기가 검수하지 않습니다.
3. **실행 확인:** 테스트가 있는 문제는 `node tools/check-tests.js`로 모범 답안 전부 통과·초기 코드 실패를 확인하고, `node tools/validate-data.js`로 스키마·배점·출처 id를 검사합니다.
4. **배포:** 검수를 통과한 문제에만 `verified`를 붙이고, `verified`가 있는 문제만 트랙 파일에 합쳐 배포합니다(`tools/merge-parts.js`가 없는 문제를 건너뜁니다).
5. **최종 점검:** 배포된 문제도 다시 점검합니다. 점검자가 고친 내용은 점검에 참여하지 않은 검증자가 다시 확인한 뒤에만 반영합니다.

### `verified` 필드

`{level, date, note}` 형식입니다.

| `level` | 화면 표시 | 뜻 |
|---|---|---|
| `executed` | 실행 검증 | 모범 답안과 숨은 테스트를 판정 서버에서 실행해 확인했고, 내용도 문서와 대조했습니다 |
| `reviewed` | 문서 대조 | 실행할 테스트가 없는 문제(면접·과외 등)로, 내용을 인용한 문서 원문과 대조했습니다 |

`note`에는 무엇을 어떻게 확인했는지 한국어 한 문장을 적고, 최종 점검 때는 `최종 점검 YYYY-MM-DD:`로 시작하는 문장을 덧붙입니다. 문제별 기록은 [VERIFICATION.md](VERIFICATION.md), 묶음별 검수 요약은 [reviews/](reviews/)에 있습니다.

## 7. 저작권·학업 윤리·보안

- 출처는 짧게 인용하고, 나머지는 자기 말로 풀어 씁니다.
- Carnegie Mellon 강의 슬라이드는 공개 라이선스가 없는 교육 자료입니다. 슬라이드 문장·그림·과제·실습·시험 문제를 문제에 옮기지 않습니다(저작권과 CMU 학업 윤리 규정).
- 회사 이름, 회사 코드, 내부 서비스 이름·주소, 키·토큰·계정 정보, 고객·매출 데이터는 저장소와 AI 프롬프트 어디에도 넣지 않습니다.
- 공개 파일(`data/`, `docs/`, `README.md`)에는 로컬 파일 경로를 넣지 않습니다.
- 문제 `id`는 학습 기록의 키이므로 바꾸지 않고, 배포된 문제는 지우지 않습니다.
